### Day 2569: Wall and Monotonic Clocks

Today I studied what Wall Clock and Monotonic Clock are. Wall clock is the time that you can see, like in a clock in your house, the time in your cellphone, TV, etc. In Java, you can know the current wall clock by using the `System.currentTimeMillis()` Java API, this API returns the current wall clock value at the moment it was executed. I see multiple times in different codebases that to measure how much time a method requires to be executed, we use `currentTimeMillis` to know that, but one of the trade-offs is that the Wall clock can be modified manually. So imagine that you have a process that runs every 1 hour and you use the wall clock to check if an hour has passed; if someone modifies the clock manually, like subtracting 10 minutes, your code will be executed 10 minutes later. I learned that a better approach is to use a Monotonic clock; this clock is like a sequence that is initialized when your PC turns on and moves forward. The advantage is that this clock is not affected by manual modifications to the PC time. So you can use it to measure the performance of a method or general benchmark code performance.

### Day 2568: Tiered Roll-off Policy

Today I was learning Tiered Storage Backup policies within Storage systems like the `Tiered Roll-off Policy`. I am investigating one of these policies that works like a First-in First-out (FIFO) algorithm; the general idea is we can have N backups of data until a limit on size is reached. The algorithm is something like `Backup size > Available Space`: delete the oldest backup and do the validation step again; do the same step as needed until you have available space to store the new backup. I learned that this Tiered policy looks very simple but has a trade-off because you can save the entire data in a backup, and next just store the delta backups (the bytes that changed), but what happens if the oldest backup deleted is the backup that contains a duplicate of the data? Well, you end with corrupted backups. This scenario is known as `Incremental Chains`, in which backups depend on other backups, and if you remove one backup within the chain, you can imagine the results.  

### Day 2567: Change Recording bitmap

Today I studied that a bitmap is just an array of bits (0s and 1s) where each bit represents an element for the bitmap context. I studied the Change Recording Bitmap data structure that can be used to know which blocks changed since a specific point in time. Imagine that you have 1,000,000 blocks, and you want to back up just the blocks that changed since the last 10 minutes; the brute-force way to do that is to review the 1,000,000 blocks with the previous version and check the ones that are not equal. That is a very expensive task; with a bitmap, you only need to analyze the bits within the bitmap and select the bits that are 0, next map the bit to a block normally by position, and that is all. You will require just `1,000,000 / 8` `int`s within the bitmap to track all the available blocks. This concept is very interesting; I have an interesting idea: write a Java application that includes the usage of Sockets, Handler, Broadcast, and Bitmap to better understand the concepts learned over the last few days.

### Day 2565: Backup Information

Today I was learning backup information techniques at the virtualization level. When we have bytes stored in a logical volume, sometimes we want to  back them up in case we need to recover the information. One common technique is to replicate the information to another logical volume in a synchronous way; we can also replicate the information in an asynchronous way. Another technique is to take Snapshots of the current volume state, so we can recover the information at a point in time, like the exact information the volume has at 00:00 midnight. One technique to take snapshots is to save the snapshot information within the same volume and not allow external access, only allowing access through special recovery software. ### Day 2564: High Availability and Disaster Recovery

Today I was learning the concepts of high-availability and disaster recovery techniques while learning the architecture of IBM Copy Service Manager technology. High-availability is when your application or system supports scenarios when your primary server is down for any reason and you have a secondary server normally in standby state, ready to be the new primary if needed. Imagine a scenario when the server running your application crashes for any reason; if you have a secondary server, you can easily make the secondary the new primary and continue working without issues. Disaster recovery technique is something similar to high-availability but is more for when something catastrophic happens to maybe the data center running your application, like an energy shutdown or earthquake. ### Day 2562: TCP Write IO Timeout Operation

Today I learned that when you perform a blocking I/O operation in languages like Java, Python, or Go, the OS kernel does not enforce a quick default timeout. If you do not set explicit timeouts at the code level, a blocking socket read will wait indefinitely if the remote peer stops sending data. While the kernel does have deep fallback mechanisms for dead connections (like TCP retransmission limits or keepalives), these take anywhere from minutes to hours to trigger, which can easily hang your application threads and exhaust resources. This was very interesting because it is something we often overlook as software engineers. Relying on default OS behavior for network I/O is risky, which is why configuring explicit timeouts in our application code is crucial.

### Day 2551: Active-Standby Architecture

Today I was studying the `Active-Standby` architecture. This architecture is used to achieve high availability in a software application. You have 2 or more nodes involved in this architecture. One is working as the primary node doing the normal activities, and the standby node normally is just idle but has the same state as the primary. Both nodes need to have the same state because in case of a failure, the standby node needs to work as the primary. Another studied concept was `Takeover/Failover` and `Split-brain scenario`. Takeover/Failure is when the standby server is promoted to be the primary. Takeover means manually the standby server is selected as the new primary and failover is when automatically the standby server is promoted to be the primary. Split-brain scenario is a common issue that sometimes happens when a network partition happens on the primary server and it loses the connection with the standby, so the failover happens but the problem is the primary is just having some networking issues that are fixed automatically some seconds later. The problem is now you have two nodes working as the primary and you will have a lot of consistency issues or errors because both nodes are doing multiple operations twice.
